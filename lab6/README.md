# ЛР 6. Розподілене навчання нейромережі за даними на CPU (варіант 26)

Згорткова мережа для класифікації зображень BloodMNIST, навчена в P процесах одного вузла за схемою паралелізму за даними (PyTorch, бекенд gloo, torchrun): ручна синхронізація градієнтів, DDP, strong і weak scaling, лінійне правило швидкості навчання, контрольні точки й відновлення після відмови.

## Параметри варіанта 26

| Параметр | Значення |
|---|---|
| Датасет | Д2, BloodMNIST: K = 8 класів, C = 3 канали, 28 × 28 |
| Ширина мережі | Ш3: c1 / c2 / h = 64 / 128 / 512 |
| P_max | 2 |
| Глобальний батч B | 192, батч процесу b = B / P_max = 96 |
| K_c (інтервал контрольних точок) | 10 кроків |
| s_f (крок відмови) | 25 |
| N (навчальна частина) | 7000 перших прикладів train; тест — увесь test (3421) |
| Оптимізатор | SGD, момент 0,9, η₀ = 0,02; η_P = η₀ · P_max = 0,04 для лінійного правила |
| n_ep | 3; `torch.manual_seed(0)` до створення моделі |
| Швидкість | 10 кроків прогріву + 50 вимірюваних; X = 50 · B / t |

**Стенд.** MacBook з Apple M5 Pro: 15 фізичних ядер (5 продуктивних + 10 енергоефективних), 24 ГБ, macOS 27.2.1; Python 3.12, PyTorch 2.15 (CPU). Усі процеси, включно з torchrun, працюють на цій самій машині (без ВМ). C_phys = 15, P_max = 2, тому n_th = ⌊15 / 2⌋ = 7 потоків на процес у всіх прогонах, включно з прогонами в одному процесі.

## Первинний проєкт (зафіксовано до коду)

**Один скрипт `train.py`**, режим вибирається параметрами. Модель, завантаження даних і формула `n_params` — дослівно з умови.

| Режим (`--task`) | Що робить | Крок |
|---|---|---|
| `info` | Стенд, `n_params` (з перевіркою `assert`), `M`, обчислене `n_e` | 1 |
| `train` з `--sync none` | Навчання n_ep епох в одному процесі без `torch.distributed` | 1 |
| `bench` | 10 кроків прогріву і 50 вимірюваних; повертає `t_step`, `t_sync`, `X`, фази кроку | 1, 2, 3, 4 |
| `grad_single`, `equiv` | Градієнт `g` в одному процесі й `ḡ` на P_max процесах на першому батчі; найбільше `max\|g − ḡ\| / max\|g\|` за тензорами | 2 |
| `sync50` | 50 кроків із ручною синхронізацією, сума ваг у float64, `all_gather`, різниця max − min | 2 |
| `--sync manual` | `broadcast(p.data, src=0)` для кожного параметра, потім `all_reduce(p.grad)` і ділення на P; `t_sync` — від першого `all_reduce` до повернення з останнього | 2 |
| `--sync ddp` | `DistributedDataParallel` з типовим `bucket_cap_mb` | 2–5 |
| `--ns` | Прямий і зворотний прохід усередині `model.no_sync()` — окремий прогін для `t_step,ns`, навчання після нього не продовжується | 2, 3 |
| `--ckpt-every`, `--fail-step` | Контрольні точки кожні K_c кроків і імітація відмови rank P_max − 1 на початку кроку s_f | 5 |

**Дані і порядок прикладів.** `DistributedSampler(shuffle=True, seed=0)` з явними `num_replicas` і `rank` працює і без `init_process_group`, тому в прогонах з одним процесом використовується той самий семплер з `num_replicas=1`. Перестановка епохи залежить лише від зерна і номера епохи, тож перші B позицій перестановки — це ті самі приклади і в прогоні з одним процесом, і в прогоні на двох (процес r бере позиції r, r + 2, …). Так порівнюються траєкторії з тим самим B. `DataLoader(batch_size=b, drop_last=True)`, `num_workers=0`.

**Кількість кроків за епоху** `n_e = ⌊⌈N / P⌉ / b⌋`: P = 2, b = 96 → ⌊3500 / 96⌋ = 36 (108 кроків за 3 епохи); P = 1, b = 192 → ⌊7000 / 192⌋ = 36 (108); P = 1, b = 96 → ⌊7000 / 96⌋ = 72 (216). Звірити з фактичним числом кроків.

**Нумерація кроків.** Глобальний крок оптимізатора нумерується від 1; `step` — номер кроку, що виконується (після кроку лічильник дорівнює числу завершених кроків). Контрольна точка записується після кроку, номер якого кратний K_c (кроки 10, 20, 30, …), `step_in_epoch = i + 1`. Відмова: rank 1 на початку кроку 25 (до прямого проходу) створює файл-позначку і викликає `os._exit(1)`. Останній завершений крок до відмови — 24, остання контрольна точка — на кроці 20, повторно виконуються кроки 21–24 (4 кроки).

**Час.** `time.perf_counter()` для швидкості; `time.time()` для подій контрольних точок і відмови (одна годинникова база для різних процесів). Журнал подій `events.jsonl`: запис контрольної точки (після `os.replace`), відмова (перед `os._exit`), відновлення, завершення першого кроку після відновлення. `t_lost = (t_f − t_c) + t_r`, `t_r` — від `t_f` до завершення першого кроку після відновлення.

**Метод вимірів швидкості.** t_step — медіана часу кроку (прямий і зворотний прохід, синхронізація, крок оптимізатора) за 50 вимірюваних кроків процесу 0; читання батча з DataLoader у t_step не входить (записується окремо). X = 50 · B / t, де t — сума 50 вимірюваних кроків. Кожну конфігурацію повторюємо кілька разів (по колу, щоб дрейф частоти і температури не потрапив в одну конфігурацію), у таблицю йде медіана повторів, розкид — окремою таблицею.

**Результати.** Кожен прогін пише `results/runs/<тег>.json` (параметри, виміри, ACC, AUC) і, для навчання, `results/runs/<тег>.csv` (втрата кожного кроку). Журнал кожного кроку умови — `results/<крок>.log` цілим одним запуском скрипта `scripts/<крок>.sh`. Таблиці і графіки будує `scripts/analyze.py`.

**Що має виявитися.** Перед вимірами очікується таке: ratio `max|g − ḡ| / max|g|` порядку 10⁻⁷–10⁻⁵ (різний порядок додавання у float32); різниця сум ваг дорівнює 0 (усереднений градієнт після `all_reduce` однаковий у обох процесах побітово); на двох процесах із 7 потоками кожен використовуються 14 з 15 ядер, але 10 з них енергоефективні, тому очікується прискорення менше 2 і залежність від розкладу потоків за типами ядер.

## Що змінилося під час реалізації

| Було в проєкті | Стало | Чому |
|---|---|---|
| `torchrun --standalone` для всіх прогонів | `--rdzv-backend=static --master-addr=127.0.0.1 --master-port=29500`, змінна `GLOO_SOCKET_IFNAME=lo0` | `--standalone` і gloo визначають адресу за іменем машини; мережа перетворює його на довгу назву `…ip6.arpa`, рандеву зависало (попередження c10d про недоступні IPv6-адреси) |
| `dist.init_process_group(backend="gloo")` зі змінних середовища | `TCPStore`-клієнт до `MASTER_ADDR:MASTER_PORT` і `PrefixStore` з номером спроби | `--rdzv-backend=static` створює сховище один раз і лишає між перезапусками, адреси gloo попередньої спроби лишаються в ньому, і перезапущені процеси чекають на мертвий порт (відновлення зависало; параметр `group_name` PyTorch ігнорує) |
| один вимір на конфігурацію | 7 повторів по колу, у таблицях медіана, розкид окремо | один вимір на цій машині (інші процеси, неоднорідні ядра) не відтворюється |
| контроль лише порівнянням із кроком 2 | додатковий прогін з контрольними точками без відмови (`s5_ckpt_nofail`) | відділити вплив самих контрольних точок від впливу відмови |
| лише параметри з умови | параметр `--max-steps` | налагодження відновлення на короткому прогоні; у прогонах серії не використовується |
