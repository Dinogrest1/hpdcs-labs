# ЛР 5. Потокобезпечна структура даних (варіант 26)

Кільцевий буфер останніх подій сервісу, до якого одночасно звертаються 12 потоків: непарні пишуть, парні читають. Синхронізація: спершу один глобальний мʼютекс, потім замок читання-запису.

## Параметри варіанта 26

| Параметр | Значення |
|---|---|
| Структура | С6. Кільцевий буфер останніх 8192 подій сервісу |
| Запис / читання | `append(e)` / `last(16)` |
| Інваріант стенду | `last` повертає не більше 16 подій з номерами, що строго спадають |
| n (потоків) | 12: непарні 1, 3, …, 11 — запис (n_w = 6), парні — читання (n_r = 6) |
| Початковий стан | Не заповнюється: заповнюються лише С2, С3, С7, С8, С10. Буфер порожній у момент запуску потоків |
| Мова | Go (`go1.27.4`); готові колекції (канали, `sync.Map`) не використовуються, лише `sync.Mutex`, `sync.RWMutex` |
| Вимірювання | прогрів 1 с (не входить), D = 10 с, 3 повтори, у таблиці медіана трьох |

## Первинний проєкт (зафіксовано до коду)

**Мова.** Go. Python 3.9 на цій машині має GIL, тож RWLock на `threading.Condition` не дав би паралельного читання: потоки читання однаково виконувалися б по одному. Go дає справжній паралелізм, а стандартний `sync.RWMutex` є тим замком, який описує умова для Go.

**Подія.** Невелика структура: номер `Seq` (uint64, присвоюється під замком при `append`, строго зростає), час створення, тип і код події.

**Структура.** Масив `[8192]Event`, індекс `head` (куди писати наступну подію), лічильник `count = min(записів, 8192)`, лічильник `seq` (номер останньої події, дорівнює кількості `append`). Запис перезаписує найстарішу подію, коли буфер повний.

**Операції.**
- `append(e)`: під замком запису `seq++`, подія отримує цей номер, записується в `buf[head]`, `head` зсувається по колу, `count` росте до 8192.
- `last(16)`: під замком читання копіює до 16 найновіших подій від новішої до старішої в буфер, який дав викликаючий потік (щоб не виділяти памʼять під замком). Поля структури лише читаються.

**Синхронізація.** Параметр запуску `-lock global|rw`. Глобальний замок: `sync.Mutex`, і `append`, і `last` захоплюють його на весь час роботи зі структурою. RWLock: `sync.RWMutex`, `append` бере `Lock`, `last` бере `RLock`. Політику `sync.RWMutex` беремо з документації встановленої версії і наводимо у звіті.

**Стенд.** n горутин, кожна закріплена на потоці ОС (`runtime.LockOSThread`), `GOMAXPROCS` типовий (15). Потік 1…n: непарні пишуть, парні читають, без пауз; аргументи (тип і код події) генеруються в потоці до виклику. Для кожної операції беруться `t_call` (до захоплення), `t_acq` (після захоплення), `t_ret` (після звільнення) з монотонного годинника Go; τ = t_ret − t_call, t_wait = t_acq − t_call. Тривалості кожної операції зберігаються (uint32, нс), перцентилі p_q = τ_(⌈q·N⌉) рахуються точно за відсортованим списком усіх операцій ролі. Прогрів 1 с і вікно D = 10 с задаються моментами часу, спільними для всіх потоків; операція входить у вимірювання, якщо її `t_call` потрапив у вікно.

**Режими.** `run` (n потоків), `x1` (один потік по черзі виконує записи і читання в пропорції n_w : n_r = 6 : 6 = 1 : 1 під тим самим замком), `cs` (t_cs,w і t_cs,r одним потоком без конкуренції: час від отримання до звільнення замка), `clock` (вартість самого вимірювання часу).

**Перевірка інваріантів.**
1. Кожен результат `last` перевіряється в потоці читання поза замком: не більше 16 подій, номери строго спадають. Лічильник порушень має бути 0.
2. Після прогону: кількість усіх `append` (разом із прогрівом) дорівнює останньому `seq`; розмір дорівнює min(записів, 8192); `last(16)` з кінцевого стану коректний.
3. Читання не змінює полів структури: (а) `go test -race` з одночасними читачами і писцями, (б) тест, що порівнює копію структури до і після мільйона `last()` в одному потоці, (в) `last` працює лише під замком читання і нічого не присвоює полям структури.

**Метрики.** X_w, X_r, X, x, φ, p50, p99, h, t_wait, t_wait,max, w, cv, t̄_cs, ρ, S(n), E(n), S_w, S_r, S_Σ за формулами умови. `scripts/analyze.py` бере медіану трьох повторів кожної величини з `results/raw/*.json` і пише таблиці 1–6 у `results/tables/`.

## Що змінилося під час реалізації

| Було в проєкті | Стало | Чому |
|---|---|---|
| Подія: номер, час, тип, код | додано поле `Sum` (контрольна сума решти полів) | читач, який побачив би напівзаписану подію, виявляє її за сумою; лише номерів для цього замало |
| `last` повертає події | повертає ще й розмір буфера на момент читання | можна перевірити, що кількість повернутих подій дорівнює min(16, розмір) |
| Інваріант умови перевіряє лічильник порушень | два лічильники: порушення інваріанта умови (не більше 16, строго спадають) і додаткові (номери без пропусків, суми, k = min(16, розмір), номер найновішої події не спадає в одного потоку) | додаткові перевірки сильніші за умову; обидва лічильники мусять бути 0 |
| Годинник `time.Now()` | `time.Since(t0)`, де `t0` взято `time.Now()` на старті | те саме монотонне джерело, але дешевше; вартість обох викликів виміряно в режимі `clock` |
| Масив тривалостей росте через `append` | шматки по 2^20 значень | `append` усередині вимірювання копіював би сотні мегабайтів |
| Операції після кінця вікна не враховуються | остання операція кожного потоку, що почалася після кінця вікна, виконується, але не входить у вимір; у «усього append» для перевірки інваріантів вона входить | кількість `append` у кінцевій перевірці мусить збігатися з `seq` |
| Перцентилі за мікросекундами | точні значення в наносекундах, але годинник macOS має крок 41,67 нс | усі окремі τ і t_wait кратні 41,67 нс; середні (з точних сум) цим не спотворюються, p50 коротких операцій округлено до кроку годинника |
